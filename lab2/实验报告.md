# Lab2 物理内存与页表实验报告

## 1. 实验目标与总体流程

本实验围绕物理内存的发现、页描述符初始化、连续物理页分配和页表启动映射展开。内核启动后已经由 `entry.S` 建立启动页表并开启 Sv39 分页，随后进入 `kern_init()`，调用 `pmm_init()` 完成以下流程：

```text
pmm_init()
  -> init_pmm_manager()
  -> page_init()
  -> init_memmap()
  -> check_alloc_page()
  -> Buddy System 检查
  -> SLUB Challenge 检查
```

当前正式使用的管理器仍为 Best-Fit。Buddy System 作为独立的 `pmm_manager` 实现保留，并在内核启动时使用独立测试页数组验证；SLUB 建立在当前页级分配接口之上。这样既保留了必做任务要求的 Best-Fit 输出，也能在同一次启动中验证 Buddy 必做任务和 SLUB Challenge。

## 2. 物理内存初始化

### 2.1 核心实现

`page_init()` 位于 `lab2_new/kern/mm/pmm.c`，主要工作如下：

1. 通过设备树接口 `get_memory_base()` 和 `get_memory_size()` 获取 DRAM 范围。
2. 设置虚拟地址到物理地址的偏移 `va_pa_offset = PHYSICAL_MEMORY_OFFSET`。
3. 根据物理内存结束地址计算 `npage`。
4. 在内核结束地址之后按页对齐放置 `struct Page` 描述符数组。
5. 将所有描述符先标记为 Reserved，避免内核镜像和描述符数组被分配。
6. 将描述符数组之后直到物理内存结束的完整页面交给 Best-Fit 管理器。

关键约束是区分虚拟地址、物理地址、物理页号和 `struct Page *`。内核结束地址及 Page 数组地址必须先通过 `PADDR()` 转换，再进行页对齐和 `pa2page()` 转换。

## 3. First-Fit 分配算法理解

First-Fit 使用一个按地址递增排列的空闲块链表。每个空闲块的首个 `Page` 用 `property` 保存块大小，并设置 `PG_property` 标志。

- 初始化时，把连续空闲页清除 Reserved、引用计数置零，并把整段页面作为一个空闲块插入链表。
- 分配时从链表头开始查找第一个 `property >= n` 的块。如果块大于请求数量，就从块头切出前 `n` 页，把剩余部分重新作为空闲块插入原位置。
- 释放时将页面恢复为空闲状态，按地址插回链表，然后检查前后相邻块并合并。
- `nr_free` 保存当前全部空闲页数量，分配减少，释放增加，合并只改变块数量而不改变页总数。

First-Fit 的优点是实现简单、分配速度较快；缺点是容易在低地址区域形成碎片，并且查找结果不一定能减少外部碎片。可以通过 Best-Fit、地址索引树、分离空闲链表或 Buddy System 改进查找效率和碎片控制。

## 4. Best-Fit 实现

Best-Fit 位于 `lab2_new/kern/mm/best_fit_pmm.c`。它沿用 First-Fit 的空闲块描述方式，但分配时遍历整个空闲链表，选择满足请求且 `property` 最小的块。分配和释放的核心规则如下：

- 找不到大小足够的块时返回 `NULL`。
- 找到更大的块时切分出剩余块。
- 释放后按地址顺序插入。
- 释放块与前后空闲块连续时分别合并。
- `pmm.c` 中将当前管理器注册为 `best_fit_pmm_manager`。

Best-Fit 仍有改进空间：当前实现每次分配都线性扫描链表，时间复杂度为 O(n)，可以使用按块大小排序的树、大小分级链表或同时维护地址索引来降低查找成本。相同大小块的选择策略也可以进一步优化，以改善局部性。

## 5. Buddy System（任务三）

### 5.1 实现位置

- `lab2_new/kern/mm/buddy_pmm.c`
- `lab2_new/kern/mm/buddy_pmm.h`

Buddy System 按 2 的幂次管理块。每个阶的链表保存大小为 `2^order` 页的空闲块。分配时将请求向上取整到最近的 2 的幂次；如果高阶没有空闲块，则从更高阶取块并不断二分。释放时根据块相对起始位置的异或结果找到伙伴，如果伙伴也空闲则合并并继续向上检查。

本实现提供了 `buddy_pmm_manager`，但不替换实验要求的 Best-Fit。启动时使用独立的 64 页测试数组调用 Buddy 管理器，避免测试消耗正式 Best-Fit 的页链表。

## 6. SLUB Challenge（选做）

### 6.1 实现位置

- `lab2_new/kern/mm/slub.c`
- `lab2_new/kern/mm/slub.h`

SLUB 采用两层结构：底层使用 `alloc_page()` 或 `alloc_pages()` 获取页，上层按对象大小建立 slab。每个 slab 保存对象大小、步长、容量、占用位图和所属 Page。小于等于一页的对象使用单页 slab；大于一页的对象使用连续页并记录在大对象表中。

为适配无 `malloc` 的内核环境，slab 元数据使用静态数组保存；对象占用状态使用位图数组记录。释放对象时先查找大对象表，再查找小对象 slab；当某个 slab 的对象全部释放后，将其页归还给 PMM。

### 6.2 SLUB Prompt 1

1. 提供 slub_init、slub_alloc(size)、slub_free(ptr) 和 slub_challenge_check。

## 7. AI 生成代码时遇到的问题与修复

1. 原始工程使用 `riscv64-unknown-elf-` 前缀，而本机安装的是 `riscv-none-elf-`。通过 Windows 构建脚本传入新的 `GCCPREFIX` 解决。
2. 新版 GCC 默认架构选项不足，汇编器拒绝 `sd` 和 CSR 指令。Makefile 增加 `-march=rv64gc -mabi=lp64d`。
3. Windows 自带的旧 TDM Make 无法启动。工程内加入 GNU Make 4.4.1 和 Windows 辅助脚本，避免依赖损坏的系统 Make。
4. Windows Git Bash 的 MSYS 子进程受到权限限制，Makefile 的 `awk/sed` 无法运行。加入项目级兼容脚本，并移除只用于依赖过滤的 shell 扫描步骤。
5. SLUB 首次编译时缺少 `string.h`，导致 `memset` 隐式声明；补充内核自己的字符串头文件后重新编译通过。
6. Buddy 测试需要临时替换全局 `pages` 以便通过页索引寻找伙伴；测试结束后恢复原指针，避免影响后续 SLUB 和官方测试。

## 8. 关键知识点与 OS 原理对应关系

| 实验实现 | 对应 OS 原理 | 说明 |
|---|---|---|
| `page_init()` | 物理内存发现与保留 | 设备树提供硬件资源描述，内核排除固件和内核占用后建立可分配区域 |
| `struct Page` | 页帧描述符 | 用软件元数据表示物理页状态、引用计数和空闲块属性 |
| First-Fit / Best-Fit | 连续内存分配 | 物理页连续分配可以直接满足页表、内核缓冲区等需求 |
| Buddy System | 伙伴分配 | 通过 2 的幂次块和 XOR 伙伴关系快速拆分与合并 |
| SLUB | 对象分配器 | 在页分配器之上复用固定大小对象空间，降低小对象分配开销 |
| Sv39 启动页表 | 地址转换 | 虚拟地址通过多级页表映射到物理页，页内偏移保持不变 |

本实验没有完整覆盖进程地址空间隔离、缺页异常、换页、TLB shootdown、NUMA、并发锁、内存回收和写时复制等更复杂的操作系统知识点。

## 9. 分支任务：GDB 调试页表查询过程

### 9.1 双层调试结构

本任务需要区分两个 GDB：

- RISC-V GDB 连接 QEMU 的 GDB stub，调试 ucore 内核、寄存器、指令和符号；
- 宿主机 GDB 附加 QEMU 进程，调试 QEMU 中模拟 MMU、TLB 和页表遍历的 C 源码。

实验文档要求重新编译带调试信息的 QEMU，并且不执行 `make install`，这样不会覆盖系统中的正式 QEMU。宿主机 GDB 的参考断点和打印命令保存在 `lab2_new/tools/gdb_qemu_pagewalk.gdb`，其中使用了 QEMU 4.1.1 中的 `riscv_cpu_tlb_fill` 和 `get_physical_address` 两个关键函数。实际操作顺序为：先用宿主机 GDB 附加 QEMU 并执行 `continue`，再用 RISC-V GDB 连接 `:1234`。

本机的正式 QEMU 可运行，但不是带 QEMU 源码调试符号的 debug build，因此宿主机侧的源代码断点需要在 Linux/WSL 或按实验文档重新编译的 QEMU 4.1.1 上执行。脚本保留了完整的双 GDB 操作方式，未将发行版 QEMU 冒充为可进行源代码单步的调试版。

### 9.2 来宾侧实际调试演示

Windows 环境下使用 `tools/debug_page_table.ps1` 启动 QEMU 的 `-S -gdb` 接口，再由 `riscv-none-elf-gdb` 执行 `tools/gdb_page_table.gdb`。脚本在 `check_alloc_page` 处暂停，此时 `kern_init` 已完成物理内存初始化，内核仍运行在启动时建立的 Sv39 页表下。

实际输出的关键部分如下：

```text
Breakpoint 1, check_alloc_page () at kern/mm/pmm.c:152
satp           0x8000000000080205
VA = 0x00000000c020166c
VPN2 = 0x1ff, VPN1 = 0x001, VPN0 = 0x001
offset = 0x66c
SATP.PPN = 0x80205, root_pa = 0x0000000080205000
root_va = 0x00000000c0205000
L2 PTE address = 0x00000000c0205ff8
0xffffffffc0205ff8:  0x00000000200000cf
```

解释如下：`satp` 的高位 `8` 表示 Sv39，低位 PPN 为 `0x80205`，所以根页表物理地址为 `0x80205000`。观测地址按 Sv39 拆分后得到三级索引 `[VPN2, VPN1, VPN0]=[0x1ff,0x001,0x001]`，页内偏移为 `0x66c`。根页表第一级项地址为 `root_pa + VPN2 * 8`；由于当前 GDB 访问的是内核直接映射区，因此脚本使用对应的 `root_va` 读取 PTE。读出的 `0x200000cf` 中 `V/R/W/X` 和访问、脏位有效，表示这是一个可继续完成地址翻译的有效映射项。

完整日志保存在 `report/logs/gdb_page_table_guest.txt`。脚本还会继续运行，便于在同一个会话中观察后续访存；宿主机 QEMU 调试脚本中的条件断点可进一步把断点限制到目标虚拟地址。

### 9.3 QEMU 地址翻译调用路径

QEMU 中可按以下路径理解一次开启虚拟地址空间后的访存：

```text
访存指令执行
  -> TCG 访存辅助函数
  -> 地址空间访问与 TLB 查询
  -> TLB 命中：直接组合页框号和页内偏移
  -> TLB 未命中：riscv_cpu_tlb_fill
  -> get_physical_address
  -> 按 SATP.PPN 和 VPN[2:0] 逐级读取 PTE
  -> 权限与 V/A/D 位检查
  -> 返回物理地址并填充 TLB
```

TLB 命中时不会再次遍历三级页表；TLB 未命中时才会进入 `riscv_cpu_tlb_fill`，再调用 `get_physical_address` 完成页表查询。关闭分页或处于机器态时，地址转换路径会退化为物理地址访问，不需要按 SATP 查找页表，这也是与开启 Sv39 时的主要差别。实际调试 QEMU 源码时，应在 `get_physical_address` 的入口观察 `address`、访问类型和 `mmu_idx`，再单步跟踪三级循环中 PTE 地址的计算。
